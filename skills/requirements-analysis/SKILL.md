# 需求分析交付链：BRD → 故事切片 → 故事卡 → 线框图

把一段业务诉求做成可评审、可排期、可验收的三件套。适用于流程重、合规条款多、交付物要签字盖章的 B 端项目——测绘、遥感、监测、质检、审批、结算这一类。

## 何时用

触发：写 BRD / 需求分析 / 业务需求文档 / 流程建模 / AS-IS TO-BE / 泳道图 / 差距分析 / 拆故事 / 故事切片 / 用户故事与验收标准 / 线框图。

不适用：

- **PRD**——产品事实、范围、验收承诺，是 PM 对交付团队的文档。
- **HLD / LLD**——系统边界、接口契约、数据一致性，是架构师的文档。
- **视觉设计**——配色、字体、图标、间距体系。
- **轻量需求**——三五张卡能说清的事，走三件套是过度工程，直接用 `user-stories` 写卡即可。

## 交付物

| # | 产物 | 回答的问题 | 读者 | 生命周期 |
|---|---|---|---|---|
| ① | BRD | 为什么做、现状差在哪、系统要满足什么 | 发起人 / 评审 / 客户 | 按评审修订 |
| ② | 故事切片 | 为什么这样切、切几片、先做哪片 | 评审 / PM | 评审通过后**冻结** |
| ③ | 故事集 | 每一片具体做什么、怎么算做完 | 开发 / 测试 | 持续演进 |
| ④ | 线框图（可选） | 屏幕上有什么、什么顺序、什么状态 | 开发 / 设计 | 随卡片变 |

**②与③不合并。** ②是跨卡片的论证——"为什么是 47 片不是 26 片"这类问题不属于任何一张卡；③是每日作业单。两者重复 As/I want/so that 是已知代价，以③为权威。合并的结果通常是论证被塞进卡片、每张重复一遍，或者干脆丢掉。

## 三条硬边界

1. **止于"写清楚要做什么"。** 不写技术方案、不选框架、不设计接口。越界会让 PM 和架构师失去判断空间，也会让 BA 的文档在评审时被当成技术承诺。
2. **不编数据。** 基线（周期、人力、人日）拿不到就写"待确认"并注明影响；从交付物反推的内容必须标「推断」。编一个看起来合理的数字，会在验收时变成债务。
3. **不宣称全部就绪。** 明确标出还需再拆的卡、未决问题（分阻塞 / 非阻塞）、以及过渡期的临时安排。

## 执行流程

### Step 0 · 摸清基线与未知（先不写文档）

产出两张清单，后面所有内容都挂在上面。

- **基线清单**：现状关键数字（周期、业务量、人力、缺陷数）。每个数字标来源：实测 / 业务方口述 / 推断。
- **未知清单**：分「阻塞」（不确认就定不了方案）与「非阻塞」。每条写明：影响哪个产物、谁来定、什么时点前要。

判断标准：如果某个目标的分母没有基线，就在目标里直接写"拿不到则降为定性目标，不纳入考核"，而不是假装能考核。

### Step 1 · BRD

按 `references/brd.md` 的十章骨架写。四个必须做实的点：

- **需求 ID 必须挂业务目标。** 挂不上的需求要么删、要么补目标。ID 一经发布不重编。
- **AS-IS 不只画流程，要画断点。** 交接点标「正常 / 弱 / 断」，每个"断"给一条有据可查的后果。
- **Out of Scope 写到条款级。** 不写"不做鸟情"，写"只提供生境图层与统计，结论由专家写"。
- **门禁 / 检查清单从真实缺陷反推。** 本期查出 9 类口径缺陷，就出 9–10 条门禁逐条对应，不从教科书抄。

泳道图与表格**同源**：HTML 内嵌 JSON 作唯一数据源，脚本生成 Markdown 表格写回文档标记区，两边都不手改。

### Step 2 · 故事切片

按 `references/slicing.md`。核心三条：

- Feature 按**流程阶段**切，不按系统模块切。
- 发布单位是**波次**，不是 Feature。每个波次从各阶段各取最薄一片，串成一份能出门的交付物。
- **失败路径属于骨架。** 阻断、回退、降级必须在第一波上线。

### Step 3 · 故事卡 + AC

按 `references/story-card.md`。每卡五段：Card / Design / Conversation / Confirmation / 元信息。

AC 分六类（行为 / 校验 / 边界 / 性能 / 可用性 / 集成）。先抽全局约定（G-1…G-n）避免逐卡重复。

**反向验证**：某片写不出可验证的 AC，说明切片是假的，回去重切。这一步能筛掉大半无效拆分。

### Step 4 · 线框图（可选）

按 `references/wireframe.md`。只画信息密度高的少数几屏，列表 / 表单页复用组件不单独出图。Design 字段写"屏 + 区域 + 约束"，不写 TBD。

起点模板：`assets/wireframe-skeleton.html`。

### Step 5 · 自检

跑 `scripts/check_storyset.py <故事集路径>`，再过 `references/self-check.md`。

数字类校验（卡片数、编号连续、字段齐全、AC 总数、波次分布）必须全过；判断类校验逐条看，过不了的写进文档而不是藏起来。

## 十二条判断准则

从真实项目里踩出来的，不是方法论。每条都带"为什么"。

**写作纪律**

1. 基线的起止点和单位没确认，就写"待确认"，并在目标里预留降级方案。
   *为什么*：起止点差一天，周期目标就是假的；验收时无法解释。
2. 从交付物反推的结论标「推断」，不与访谈确认的事实并列。
   *为什么*：推断被引用一次，下次就变成"我们说过"。
3. 需求 ID 必须挂业务目标，挂不上就删。
   *为什么*：不挂目标的需求永远排不上优先级，也不会被砍。
4. 权限与责任写进文档，不留给开发拍板。
   *为什么*：谁判定、谁确认、谁签发，决定出错时谁负责。

**切分判断**

5. Feature 按流程阶段切，同时说清"为什么这不是横向切分"——Feature 是 backlog 组织单位，纵向由波次保证。
   *为什么*：不解释，评审时会被当成按模块切而打回。
6. 失败路径进第一波，不进"后续优化"。
   *为什么*：缺陷漏出往往不是因为没检查，是因为检查没有出口。
7. 有外部数据依赖的能力单独切片，并把"数据缺失时只能输出什么"写进 AC。
   *为什么*：捆在一起会让整片被数据卡死，项目整体停摆。
8. 每一次"合并"都要能说清失败后果不同；后果相同就该合并，后果不同就不该。
   *为什么*：切得太碎会产生一堆无法单独验收的半成品。

**验收判断**

9. AC 缺哪一类，就在对应阶段暴露：行为→无法演示；校验→缺陷漏出；边界→空态崩溃；性能→目标不可验；可用性→现场误用；集成→交付物接不上。
   *为什么*：六类不是模板，是六种失败模式。
10. AC 条数不等于用例数。写清"合并同类项后大约多少条"。
    *为什么*：按 AC 条数排测试工作量会严重高估。

**呈现判断**

11. Design 不写 TBD，写"屏 + 区域 + 约束"。
    *为什么*：几十个 TBD 会被读成"还没想清楚"；同样没有图，"线框待出"是计划。
12. 状态不用颜色区分：异常用斜纹，待补用虚线，当前项用反白。
    *为什么*：判读类界面靠颜色区分结论，色觉障碍会直接导致误判。

## 工程约定

- **大文件批量改动走 python 直写**，不用逐条编辑。编辑器路径可能把 `1. ` 转义成 `1\. ` 并补行尾硬换行，破坏有序列表语义。真实事故：一次批量替换丢了整段故事卡，且无版本库可回退。
- **每次批量改动后必跑校验**：改前记下数量、编号连续性、字段齐全、AC 总数、分布；改后必须一致。不一致就回退重做。
- **图表类产物用无头浏览器截图验证**：`"/Applications/Google Chrome.app/Contents/MacOS/Google Chrome" --headless=new --screenshot`。中文路径先复制到 `/tmp` 英文路径，否则不出图。
