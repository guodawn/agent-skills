# 线框图

线框要回答的是「屏幕上有什么、按什么顺序、什么状态」，不是「好不好看」。任何视觉决策都会把评审引向品牌讨论，而那不是这一轮要解决的问题。

## 先分屏，再画图

不要一张卡一张图。按**界面归属**把卡片归并成屏，通常 3–5 屏就能覆盖全部。

| 屏类型 | 典型内容 | 线框优先级 |
|---|---|---|
| 主工作台 | 列表 + 详情，人一天里待最久的地方 | **高**——交互设计直接决定人力目标能否成立 |
| 详情 / 表单页 | 单对象多区块 | 中 |
| 长文档预览 | 目录树 + 正文 + 状态侧栏 | 中 |
| 检查 / 审批列表 | 逐项结论 + 定位 + 操作 | 低，用通用列表组件 |
| 工单 / 档案 | 列表 + 登记表单 | 低，同上 |

判断标准：**如果这一屏的交互形态会决定某个业务目标能否达成，就必须画。** 例如"每天判几十个对象"的工作台，信息密度和键盘流直接决定人日，那它就不是装饰，是目标的一部分。

寄生型界面不要单独出屏：某个卡片的界面落在别的屏里（报告里的某一章、列表里的某一列），在文档里注明归属即可。

## 低保真契约

- 灰阶。系统字体。细边框。不用阴影、渐变、品牌色、装饰图。
- **真实文案**。不写 lorem ipsum，不用匿名方块——文案长度会影响布局判断（"疑似超高 · 待确认"比"状态"长得多）。
- 图片与富媒体用带标签的占位块。
- 批注只标"暴露出来的假设、开放问题、无法直接演示的行为"。批注写**为什么这样排**，不写"这是什么"——后者看界面就知道。
- 单文件自包含 HTML，无外部依赖，浏览器直接打开，可打印。
- 键盘可操作：切屏、切条目、提交都要有键位。

## 状态表达：不用颜色

这是本项目最重要的一条约定，也顺手解决了可访问性要求。

| 状态 | 表达 |
|---|---|
| 常规 | 实线边框 + 浅填充 |
| 异常 / 未过 | 斜纹填充 + 文字（"不达标""不通过"） |
| 待补 / 占位 | 虚线边框 |
| 当前项 / 已选 | 反白（深底白字） |
| 不可用 | 灰字 + 右侧原因列 |

理由：判读类界面天然想用红黄绿区分结论（如四档判定），色觉障碍用户会直接误判。用纹理和文字替代颜色，信息量不减，人群覆盖更全。

**"不可用"与"0"必须在视觉上可区分**。数据缺失输出 0 会被读成"没有"，这是实质性误导。

## 一份屏的组成

```
标题栏：对象 + 关键上下文 + 状态标签 + 主操作
主体：区块化，每块一个 cap（标题 + 批注号）
底部：批注列表（编号对照）+ 快捷键/性能提示
```

性能提示放在界面上（"打开 ≤ 1.5 s""图幅 ≥ 800×600"），因为这类指标是验收口径，不是实现细节。

## Design 字段怎么写

不写 TBD。写三件事：

```
**Design**：屏 B · 限高初判区（[线框 B](线框.html#B)）｜约束：四档 + 依据三要素 + 数据来源；声明句锁定
```

- **屏 + 区域**：开发不用等设计交付就知道界面在哪。
- **约束**：这一块必须成立的条件（等权、锁定、精度、图幅）。
- 链接指向可运行的 HTML 的锚点。

几十个 TBD 会被读成"还没想清楚"。同样没有图，"线框待出，见附录 G"是计划，"TBD"是缺口。

## 刻意不做的事

写进文档，避免被追问：

| 不做 | 原因 |
|---|---|
| 视觉设计（配色、字体、图标、间距体系） | 会引发品牌评审，不是本轮议题 |
| 交互原型（跳转、动效、模拟数据） | 流程逻辑在 AC 里，不在线框里 |
| 移动端重排 | 内网桌面端场景，只保证窄屏不横向溢出 |
| 空态 / 错误态全量覆盖 | 只画最关键的 3 个，其余开发时按 AC 补 |

## 验证

渲染后截图逐屏看：阅读顺序、换行、溢出、焦点可见性、每条已实现的点击路径。中文路径截图前先复制到英文路径，否则可能不出图。
