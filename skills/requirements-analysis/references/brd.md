# BRD 骨架

十章。每章给"必须回答什么"和"最常见的敷衍写法"，后者比前者更有用——大部分 BRD 失败在敷衍，不在缺章。

## 十章速查

| # | 章节 | 必须回答 | 常见敷衍 |
|---|---|---|---|
| 1 | 执行摘要 | 现在的问题是什么（≤3 条，带证据）；引入系统后哪些环节改变；**不承诺什么** | 罗列功能，不说问题；承诺"大幅提升效率" |
| 2 | 业务目标 | 每个目标有可测指标、现状值、目标值、期限 | 只有方向没有数字；数字没有现状基线 |
| 3 | 项目范围 | In / Out 都写到条款级 | Out 只写"其他场景不做" |
| 4 | 现状 AS-IS | 流程步骤、耗时、业务量、交接点、分支、回流 | 只画流程，不标断点；不写业务量 |
| 5 | 未来态 TO-BE | 人机分工、并行点、检查点及其恢复路径、异常分支去向 | 只说"自动化"，不说谁决定、失败了怎么办 |
| 6 | 业务需求 | 每条：ID、行为、优先级、来源、支撑目标 | 写成功能清单；来源写"需求调研" |
| 7 | 假设与依赖 | 每条假设写"不成立时怎么办"；每条依赖写"不到位时降级成什么" | 只列不写后果 |
| 8 | 约束 | 时点、规范、形式、数据口径、责任 | 混进需求里，读者分不清约束和功能 |
| 9 | 风险 | 可能性 / 影响 / 应对，应对要具体到动作 | "加强沟通""密切关注" |
| 10 | 审批 | 角色、姓名、签字、日期 | 空表 |

## 第 4 章：AS-IS 怎么写才有用

泳道矩阵（角色 × 阶段）+ 四张附表，缺一不可：

1. **交接点表**：`# | 从→到 | 传递物 | 状态（正常/弱/断） | 后果（有据可查）`
   "断"的每一行必须给一条能从交付物里指出来的证据，否则只是印象。
2. **分支表**：`判断点 | 应走的分支 | 现状`。列的是"本该有但没有"的分支。
3. **回流表**：`回路 | 从→到 | 用途 | 现状`。通常现状是 0 条。
4. **痛点表**：按浪费类型归类（等待 / 返工 / 交接 / 过度加工 / 手工操作），每类给证据。

读法要在图下写一句：某条泳道占了几格，说明什么。不写读法，读者会数格子但不知道数它干嘛。

## 第 5 章：TO-BE 的三件事

1. **人机分工**：哪个阶段机器主导、哪个阶段人必须出现、为什么。
2. **检查点而非关卡**：每个 ✋ 写 `位置 | 停下来的条件 | 人做什么 | 恢复条件`。没有"恢复条件"的检查点就是关卡，会把流程卡死。
3. **异常分支的去处**：影像不达标回哪、模型漏检回哪、自校不过怎么办。每条异常都要有路径，否则等于没有。

并行要画在同一列的不同泳道，不要写"可以并行"——写"可以并行"而图上串行，是评审必被抓的点。

## 第 6 章：需求表的写法

```
| ID | 业务需求 | 优先级 | 来源 | 支撑目标 |
```

- **ID 格式** `BR-001`，一经发布不重编。删掉的需求留号不复用。
- **业务需求写"系统应表现出什么行为"**，不写实现方式。"系统应在新影像到位后自动校验分辨率、时相、云量、投影"合格；"系统应调用 GDAL 做投影校验"不合格。
- **优先级用 MoSCoW**。Must 太多说明没排序——一份 BRD 里 Must 超过 70% 就要重新谈。
- **来源必须可追溯**：缺陷编号、访谈纪要、条款、评审意见。写"业务需求"等于没写。
- **支撑目标**：挂不上任何目标的，删。

## 附录：门禁 / 检查清单

从真实缺陷反推，不从教科书抄。

```
| # | 检查项 | 覆盖缺陷 | 判定 |
```

一期查出 9 类缺陷，就出 9–10 条，每条注明覆盖哪一类。判定要写"完全一致""无缺失"这类可机器判的表述，不写"符合要求"。

门禁与自校规则分开：自校在计算环节执行（指标 vs 明细），门禁在交付前执行（文档 vs 数据）。重复列会导致两边都以为对方在查。

## 附录：待确认清单

分两组，不要混：

- **阻塞项**：不确认就定不了方案。每条写清影响哪个产物。
- **非阻塞项**：可以边做边定。

去重。同一件事在两处出现，评审时会问两遍，答两遍，然后得出两个不同答案。

## 附录：术语与引用约定

开头就写。至少包括：

- 法规 / 标准的全称、文号、施行日期、本文简称。
- 容易数错的量（如"9 项指标"实为 1 个分类维度 + 8 项可计算指标）——**在文档里统一，并在首次出现处说明为什么改口径**。
- 周期口径：从哪到哪、日历日还是工作日。
- 「推断」标记的含义：从交付物反推、未经业务方确认、不能当事实引用。

## 泳道图与表格同源

一份数据两个视图，否则必然漂移。

```
HTML（内嵌 JSON，人看）  ──脚本──▶  Markdown 表格（机器读，写回 BRD 标记区）
                          └──────▶  PNG 快照（插入 Word）
```

约定：

- 唯一数据源 = HTML 内嵌 JSON。表格与 PNG 都是派生物。
- BRD 里用 `<!-- BEGIN:xxx-matrix -->` / `<!-- END:xxx-matrix -->` 标记，脚本按标记替换，不要用字符串匹配（旧块为空时会插到标题下面）。
- 一致性检查做成默认行为，不一致返回非零，可挂进提交前钩子。
- 版本化：BRD 升版时另存一张图，不要覆盖旧图——评审要能对比。

## 用例模板

```
### UC-00x 名称
Actor：主 / 辅
前置条件：
触发：
主流程：1..n（每步一个可观测动作）
备选流：编号对应主流程步（如 4a / 5b）
异常流：
后置条件：
```

备选流的编号必须锚在主流程的某一步上（`5b` 表示第 5 步的第二种走法）。不锚定，读者无法把分支放回流程。
